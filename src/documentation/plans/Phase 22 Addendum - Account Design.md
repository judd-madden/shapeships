### 2.1 Data model and access

**L1* — Public, prefixed tables reached through existing service-role supabase-js/PostgREST.** Reason: works with the current server seam without exposing a new schema or adding a direct SQL connection. Alternatives rejected: browser Auth access, account KV records, or a private schema requiring exposed wrapper RPCs/custom connection configuration.

All columns below are NOT NULL unless marked nullable. Tables have RLS enabled with no policies for browser roles. Independent UUID IDs default to `gen_random_uuid()`; account-ID, session-ID and composite keys retain L1* (owner-confirmed for set 01). No sequences. Times are `timestamptz` in UTC, and foreign keys point only to these account tables, not `auth.users`.

**L2* — Deny browser roles and use service-role-only SECURITY INVOKER RPCs.** Reason: combine privilege isolation with RLS and preserve existing privileged server access. Alternatives rejected: relying on RLS alone, browser-owned policies, SECURITY DEFINER elevation or unrestricted RPC execution.

- Revoke all privileges from `PUBLIC`, `anon` and `authenticated` on each new table and sequence, and revoke their function EXECUTE; explicitly grant only required table/sequence privileges and RPC EXECUTE to `service_role`. Do this before committing each SQL set. No identity/credential views or realtime publication.
- RPCs use **SECURITY INVOKER**, `search_path = ''` and fully qualified objects. `service_role` bypasses RLS; invoker functions do not grant authority to callers lacking privileges. Supabase recommends explicit execution controls: [database functions](https://supabase.com/docs/guides/database/functions).
- Do not alter schema-wide default privileges for unrelated objects in this pass series. Counter their inherited grants explicitly per object, then verify actual ACLs, RLS and absence of policies. LA10 approves set 01 browser-grant revocation on all four inventoried KV tables, with no row/index changes. Account tables grant service_role SELECT/INSERT/UPDATE/DELETE only (owner events omit UPDATE); reset inherited service_role ALL before those grants.
- RPCs have short work and bounded rows; no password hashing or network calls inside a transaction. Every UPDATE/DELETE has a WHERE clause for safeupdate, including owner and cleanup routines. Lock rows in stable order and return conflicts promptly rather than wait through the eight-second API timeout.

**L3* — Transactional service RPCs with constraint-backed claim uniqueness.** Reason: PostgREST client calls cannot group separate inserts atomically. Alternatives rejected: lookup-then-insert, multi-request compensation or browser-asserted ownership.

- `account_claim`: receive validated display/key, encoded hash/format, first token hash, validated session ID, and five preference values; recheck moderation/reservation and insert all account rows plus session link in one transaction. Claims take a shared transaction-level advisory lock on one fixed name-rules lock key; owner rule changes take the exclusive form of that same lock, so a contains-rule edit also serializes correctly. UNIQUE name_key means exactly one same-name claim wins; map its specific conflict to NAME_TAKEN. Any other failure rolls everything back.
- `account_finish_signin`: after Edge verification, compare the observed credential/security version under lock, then issue token and link. A concurrent reset/block must cause rejection, not mint a usable token from a stale password verification.
- Token authorization/renewal, logout, implicit session linking, password change, preference updates and owner reset/block use short RPC transactions. Account writes lock and revalidate token/status/security version within the same transaction, including commit-time authorization. Inputs never contain trusted account IDs from the browser.
- No pg_cron dependency. Opportunistic cleanup deletes at most 100 expired counters/revoked-or-expired tokens per successful account entry operation, at most once per minute per worker as an optimization, with row-level bounds in the RPC. Owner cleanup handles a backlog in repeated batches. Worker memory is never the source of truth for rate limits or expiry.

**L4* — Manual numbered SQL packages outside migrations.** Reason: match Judd's SQL-editor workflow and avoid accidental CLI application. Alternatives rejected: automatic migrations, unversioned Dashboard edits or combined unreviewable scripts.

- Folder: `supabase/manual/account/`; each set has `NN-forward.sql`, `NN-verify.sql` (one SELECT yielding a structured result), `NN-rollback.sql`, and its pass notes. Set 01 ships in 22C.1.
- Forward scripts run in one transaction, acquire only short locks and fail if preconditions drift. Do not change KV rows or indexes. LA10 authorizes only anon/authenticated grant revocation on the four named KV tables; service_role/postgres grants remain untouched.
- Set 01 checks `screen_names` is still empty, explicitly removes the two named policies, FK and unique constraints (their backing indexes disappear), drops the remaining created_at index and table with RESTRICT. No public functions/views/ordinary triggers need dropping. Leave platform event triggers and the Auth user alone. Stop on unexpected dependencies or nonzero rows; never use CASCADE to hide drift.
- Rollback restores the empty stub's inspected columns, constraints/indexes, policies and inventoried default grants; it does not recreate a deleted Auth user or reverse separate index maintenance. Reverse later SQL sets before earlier ones. Capture object signatures in each verification/rollback package. Exact prior KV ACL letters were not inventoried, so rollback re-grants ALL, an approved harmless superset under existing RLS. Both scripts validate every precondition before changes, run as one transaction and use no transaction-incompatible commands.

### 2.2 Passwords

**L5* — Argon2id through pinned `npm:hash-wasm@4.12.0`.** Reason: OWASP's preferred memory-hard algorithm, with embedded Wasm and Deno support, avoiding native modules. Alternatives rejected: bcrypt's legacy status/72-byte constraint, scrypt's higher default memory, and PBKDF2 as the first choice when Argon2 is viable. Sources: [OWASP parameters](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html), [library v4.12.0](https://github.com/Daninet/hash-wasm/tree/v4.12.0), [hosted Wasm support](https://supabase.com/docs/guides/functions/wasm). Hosted compatibility remains to be measured, not assumed from those sources.

| Decision | Locked contract |
| --- | --- |
| Parameters | Argon2id v19, memory 19,456 KiB (19 MiB), iterations 2, parallelism 1; random 16-byte salt per credential; 32-byte hash; encoded PHC output. Meets the cited OWASP minimum. |
| Input | Minimum 10 and maximum 128 **Unicode code points after the chosen normalization**, maximum 512 UTF-8 bytes after normalization. Reject malformed Unicode and oversized raw request bodies (8 KiB total account JSON cap); reject normalized over-limit passwords, never truncate or trim. Permit whitespace and all well-formed Unicode, with no class rules. |
| Normalization — **O1 answered** | NFC, locked before the first hash. Current [NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html) recommends NFC. No full NIST-compliance claim or change to the approved 10-character minimum. |
| Client parity | Claim form counts code points of the same normalized input, not UTF-16 `string.length`. Server remains authoritative. Shared fixtures cover astral characters, combining marks and compatibility characters. |
| Format / migration | Store a format identifier `nfc-argon2id-v1` alongside the PHC hash. Verification applies the recorded policy. Rehash on successful sign-in when parameters become outdated; compare-and-swap against the hash/version that was verified. Do not reinterpret old normalization formats silently. |
| Plaintext | Normal request hashing/verification runs only inside Edge. Never send passwords to SQL, log bodies or persist them in browser storage. The approved local owner command in §2.8 is the sole offline exception; it hashes the generated temporary secret locally with the same parameters. |
| Hash admission | Four concurrent hash jobs maximum per worker, including verification and rehash. Acquire before starting work; release in finally. No unbounded queue: a fifth request gets 503 AUTH_BUSY with Retry-After: 2. This is capacity, not a bad password or abuse throttle. |
| Memory | Four × 19 MiB = 76 MiB algorithm working memory. Budget another 16 MiB for Wasm/temporary overhead and reserve at least 128 MiB for runtime and simultaneous gameplay: planning total 220 MiB against 256 MiB. These are estimates, not measurements; include retained Wasm memory/GC peaks and warm workers in profiling. Eight hashes would already use 152 MiB before overhead, so no uncapped Promise.all. |

### 2.3 Remembered sign-in

**L6* — One opaque bearer token per browser sign-in, 32 cryptographically random bytes, base64url encoded; store only SHA-256(token) in Postgres.** Reason: high entropy makes fast token hashing appropriate, unlike passwords. Alternatives rejected: plaintext tokens in DB, self-contained long-lived JWTs without immediate revocation, or rotating every request and racing sibling tabs.

- **A1 / LA6c:** 90 days idle, no absolute lifetime initially. On accepted account-token use, renew atomically at most once per hour per token: `last_used_at = renewal time`, `expires_at = last renewal + 90 days`. Reads/polling never require account validation/renewal. Intents carry account tokens; zero throttle would write per action. No background identity-renewal polling.
- **L6*:** token goes in `X-Account-Token`, never Authorization, URL, logs or body error messages. LocalStorage key `shapeships.accountToken.v1` supplies remembered return and same-origin sibling tabs; fall back to in-memory sign-in if storage is unavailable, with no claim of cross-visit persistence. Cross-origin Edge cookies would be third-party; do not rely on them. LocalStorage bears an XSS risk: keep script trust restricted and never render untrusted markup.
- **L6*:** add X-Account-Token to CORS allowHeaders and Retry-After to exposeHeaders. Use PUT for preference updates, retaining existing allowed methods; no credentialed cookies are needed with `*`. Send no-store on account responses. Retain the anon gateway headers and per-tab game header unchanged.
- **L6*:** logout revokes that token and detaches every session linked through it, including sibling tabs; other browser sign-in tokens survive. Reset/block/password change revoke all account tokens and detach all links, advancing security_version so cached/stale authority cannot survive. Unblock does not revive credentials/tokens already revoked.
- **L6*:** on deliberate logout capture the current token, immediately remove matching shared storage, set a tab-local logout/generation fence and broadcast a storage/BroadcastChannel event. Ignore responses started under an old generation and never let resume responses recreate a token; best-effort revoke any fresh token returned by a now-stale sign-in/claim response. POST logout uses the captured token once; revoked/expired/missing credentials still clear local state. ### 2.4 Accounts and game sessions

**L7* — Transactional account-session links alongside unchanged KV game sessions.** Reason: preserve participant identity and make link/revocation atomic without dual KV-copy mutation. Alternatives rejected: using account ID as player ID, copying account authority into client state, or trusting a stale account ID embedded in KV forever.

- Validate X-Session-Token first. Link its `sessionId` to the token's server-derived account ID/display name in `account_session_links`; do not write the raw account token into KV. The identity resolver reads the live link, token revocation/expiry/security version and account status. A link alone never grants account authority without a matching valid X-Account-Token on that request.
- Claim/sign-in/password change link the current session transactionally. `/session/start` with A and resume with optional S also link the validated session; resume without S leaves game sessions unchanged. Claim never calls clearSession/clearPlayer or changes participant ID. No auto-new session recovery during a match.
- Active link to a different account produces SESSION_LINK_CONFLICT; sign out the existing account before switching. Validity derives from token/account state. Logout/reset/block/password change detach links. No link revisions or explicit link/unlink endpoints. Serialize on the session binding, including first insert through its PK; on conflict recheck active ownership rather than overwrite it. This handles the simultaneous-first-link race without client revisions. Bootstrap may have no name; game creation requires a server-approved bound name.
- New account-owned participants carry a server-assigned accountId as provenance while keeping their session-derived id. Existing guest participants retain their names/history when the same session claims a different name; new seats use the claimed display name. A guest game does not become account-owned merely because its label matches. Record the validated claim/session association for 22D; do not implement import or cross-device seat transfer here.
- On intent/chat, rejoin and other account-owned seat operations, require the live linked identity to match the participant's stored accountId; when mode is `on`, never downgrade a seat to guest authority if a header is omitted. In other modes use existing game-session authority so games cannot freeze during emergency disable. Game-state/head/history and other read/polling routes never require account validation. 22D needs durable account-to-participant evidence for imported guest runs and cross-device rejoin: expiring token/link rows alone are insufficient. 22D must record that durable evidence before its import/rejoin features and public activation; 22C's transient links must not be treated as permanent ownership proof.
- **O6 answered / LA6:** when mode is on, logout suspends account-owned seat actions until the same account relinks; it does not resign/delete the seat or reset streaks. Legacy guest seats keep existing participant/session authority under §2.6. No account mutation is allowed by a detached link. Reset similarly requires reauthentication; block denies account-owned actions and account operations while on. Read/polling routes remain exempt, and non-on modes use existing game-session authority. Current 24-hour game-session expiry still applies.
- Account writes and logout/reset/block serialize on token/account rows: writes committed before revocation stand; writes behind it fail. An already authorized KV game request may finish after logout, but cannot mutate account data or obtain new account authority. Later requests must revalidate. State this explicitly in client handling; a broadcast is UX coordination, not the security control.
- Guest Change Name retains its Entry role; audit/reuse its clearing deliberately, not for claim. Account logout uses account lifecycle operations, not the old fake logout. Cross-device rejoin and streak reconciliation remain 22D, requiring verified participant ownership, idempotent result evidence and stale-import protection, not a name match.

#### Renewal, limits and client obligations

Guest TTL is 24 hours after lastRenewedAt, falling back to createdAt; createdAt never changes. requireSession carries lastRenewedAt from its existing read. Non-due accepted intents do zero extra DB operations. A due attempt rechecks the token row and uses at most token read + token CAS + mirror read + mirror CAS, with no retries and only one successful renewal per hour. CAS preserves bound names; errors/conflicts are silent and a mirror failure cannot roll back the authoritative token write. No response gains this field. Rejected intents, reads, polling and unrelated mutation routes do not renew.

Resume/preferences/logout share the existing 120/recognized-token/minute scope and unknown-token 120/trusted-IP/minute scope. ### 22C.5a runtime API — 23 November 2026

Client-runtime implementation of §2.16 only. There is no App, Entry/menu, game-request, session-start or player-name wiring in this pass. The server remains authoritative. Modules are under `src/game/client/account/`; importing them creates no store, accesses no browser storage and starts no request.
