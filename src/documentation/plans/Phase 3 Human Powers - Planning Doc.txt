🔵 Phase 3.0A — End-of-Turn Resolution Hardening (Do This First)
Goal

Make end-of-turn resolution:

Deterministic

Simultaneous (no order bias)

UI-friendly (explicit deltas)

Future-proof for doubling, modifiers, destruction

Cleanly integrated with victory

Everything else in Phase 3 builds on this.

What you currently have

Inside resolvePhase('battle.end_of_turn_resolution'):

Collect effects from structured powers

Apply effects sequentially via applyEffects()

Clamp health to max 35

Check victory

Emit event(s) 

shapeship-rules

What’s missing or fragile:

Damage/heal are applied in sequence, not as a single simultaneous net result.

There is no explicit per-turn delta structure stored for UI.

Doubling logic (Science) and dice modifiers will complicate order if not centralized.

There’s no explicit “aggregation stage” before mutation.

Required Changes

0️⃣ Enforce the health mutation boundary (new)

Health must not change in any earlier phase (including charge declaration / charge resolution).
All Heal/Damage-producing actions should write into a per-turn accumulator (pendingTurn) and only be applied during battle.end_of_turn_resolution.

Recommended state shape:
pendingTurn: {
  damageByPlayerId: Record<PlayerId, number>,
  healByPlayerId: Record<PlayerId, number>,
  entries?: Array<{ source, amount, type, meta }>, // optional for logs/debug
}

This keeps simultaneity true and prevents order bugs when you introduce doubling/modifiers.

1️⃣ Introduce an aggregation stage (before mutation)

Instead of:

applyEffects(effect1)
applyEffects(effect2)
...


Do:

Collect all Effect[]

Reduce into per-player totals:

totalDamageByPlayer

totalHealByPlayer

Compute:

newHealth = clamp(oldHealth - damage + heal)


Apply results in one pass.

This guarantees:

True simultaneity

No order dependency

Clean insertion point for future modifiers

You can implement this directly inside resolvePhase.ts without new files.

2️⃣ Store health deltas for UI

Add to state (or projection):

For each player:

lastTurnDamage
lastTurnHeal
lastTurnNet


Or simply:

lastHealthDelta


But storing both damage and heal separately is better for debugging and logs.

This feeds:

The green/red delta numbers under health

Battle log clarity

Replay accuracy

3️⃣ Victory evaluation after aggregation

Victory should occur after both players’ new health is computed.

Rules:

Both <= 0 and equal → mutual destruction draw

Both <= 0 and unequal → higher health wins

One <= 0 → other wins

Otherwise → continue

You already have most of this logic; just ensure it runs after aggregated health application and not inside per-effect logic.

4️⃣ Keep max-health clamp here

Clamping to 35 stays here.

Even though line cap is deferred, health cap belongs here.

Why this must come first

If you implement:

Science Vessel doubling

Leviathan dice overrides

Count-based damage

Trigger-based Frigate damage

Interceptor 5-damage charge

…before this is hardened, you will end up debugging:

“Why is damage doubled twice?”

“Why does heal cancel damage incorrectly?”

“Why does order matter?”

Fixing resolution first prevents cascading bugs.

Chunk 3.2.5 — Server-projected preview totals (Build Draft)

Goal
While in build.drawing, the current player sees preview totals update as they click ships, before Ready.

Server changes


Preview/resolution identity (normative)

Introduce ONE pure computation function on server and reuse it everywhere:
computeTurnTotals(state, { draftCounts? }) -> { damage, heal, bonusLines, notes }

Use this for:
• build.drawing myPreview projection
• post-reveal “actual pre-charge” totals projection
• battle.end_of_turn_resolution aggregation inputs

This prevents preview drift and guarantees that the only difference between preview and reality is state changes (destruction/charges), not duplicated math.

Add a new intent (or extend existing build intent family):

BUILD_DRAFT_SET (recommended, idempotent): payload is the current draft counts, not “+1”.

Example: { DEF: 2, FIG: 1, ... } for this turn.

Store draft per player per turn (e.g. state.pendingBuildByPlayer[playerId] = { turnNumber, counts })

In /game-state projection:

Return requester-only fields like:

myPreview: { damage, heal, bonusLines }

Return opponent “actual” (from revealed fleet) as usual.

After opponent reveals, both sides can see opponent actual totals (pre-charges).

Preview computation uses the same server logic you’ll use for real resolution later (so preview may change if destruction/charges alter reality — which you already accept).

Client changes (useGameSession only)

On ship click in build.drawing:

Update local draft counts (you already do this in Phase 1/2 wiring style).

Send BUILD_DRAFT_SET with the full draft snapshot (debounce optional).

Display:

Whenever ships are added to fleet during any build phase: show myPreview.* as the “preview” numbers.

Once both reveal: show both players’ “actual pre-charge” totals (server truth).

When charges are used: totals update immediately from server state (as you described).

At start of next turn / when leaving build.drawing: clear draft (client + server).

This keeps the client “dumb” and preserves the “single integration seam” rule. 

Preview totals should use effectiveDiceRoll for any dice-dependent preview (e.g., Frigate trigger once chosen).

Chunk 3.4 — Ship “power memory” (persists through destruction)

Objective: support once-only persistence + Frigate trigger selection.

Server changes

Add a powerMemory structure to state. Keep it minimal and generic:

powerMemory.onceOnlyFired: Record<shipInstanceId, true>

powerMemory.frigateTrigger: Record<shipInstanceId, number>

(Optionally later) powerMemory.custom: Record<shipInstanceId, any>

Destruction rule

When a ship is destroyed, do not delete its memory. Move it to 'The VOID' which will be a space on the battlefield where destroyed ships go (their opacity will be reduced to 25%, ships will still stack if multiple)


Once-only resolution note (important)

For “once only on the turn it is built” powers:
• Gate by ship.createdTurn === state.turnNumber
• AND powerMemory.onceOnlyFired[instanceId] not set

If the rules intend the once-only effect to still resolve even if the ship is destroyed before end-of-turn, then the resolver must not require the ship instance to still exist at resolution time — it should rely on createdTurn + memory.

Acceptance criteria

STA once-only cannot be re-triggered via rebuild/destruction edge cases.

Frigate trigger persists for that instance even if it leaves play (if that’s rules-accurate for your game; otherwise keep memory but irrelevant).
