Phase 4 Xenite Powers
Normative Planning Document

Project: Shapeships
Status: Planning
Scope: Xenite powers implementation sequencing after Dreadnought

1. Purpose

This document defines the normative implementation plan for Xenite powers following completion of the Human Dreadnought pass. Its purpose is to group Xenite ships by implementation shape, maximize reuse of existing server-authoritative frameworks, and defer ships with custom rule requirements into dedicated later passes.

2. Planning Principles

Prefer reuse of established Human-side frameworks wherever the Xenite power shape is materially the same.

Bundle ships together only when they share action plumbing, state requirements, and resolution semantics.

Defer powers that introduce new timing hooks, new counting semantics, or new replacement / immunity rules into dedicated passes.

Use canonical JSON definitions as the authoritative source for power behavior.

Treat this document as the sequencing authority for Xenite implementation planning. Individual later slice documents may refine file plans, but must not silently widen scope.

3. Reusable Frameworks Already Established

The Xenite plan should reuse the following implementation families already present or actively established in the Human work:

Static automatic effects: flat damage and flat heal effects resolved server-authoritatively.

Computed automatic effects: count-based, type-based, once-only, and capped effects derived at resolution time.

Charge choice actions: ship-specific actions that spend charge and choose between multiple outcomes.

Ships-that-build actions: build-phase choices that create ships in future build phases.

Destroy targeting: targeted destroy actions with explicit valid target derivation.

Line-generation hooks: powers that add future generated lines.

Per-ship memory / once-only support: authoritative storage for built-this-turn or already-used-style conditions.

4. Phase 4 Scope Decision

Phase 4 is defined as a Xenite powers program, not a generic economy / eligibility / upgrades cleanup pass. The immediate goal is to extract the largest coherent set of Xenite ships that cleanly maps onto existing frameworks and can be implemented with limited new system surface.

5. Pass Structure

The Xenite program is split into an initial reuse-heavy pass and several later dedicated passes. This structure is normative unless a later code review proves that a deferred ship can be absorbed without introducing new framework complexity.

7. Clarifications Incorporated Into This Plan
7.1 Evolver

Evolver does not require generic friendly targeting. It can only act on a Xenite. The action model is therefore narrower than Guardian-style targeting: the ship either converts one available Xenite into Oxite or Asterite, or Holds if no Xenite exists.

Normative interpretation:

Evolver needs a Xenite-only conversion action, not a generic target picker.

Expected server shape: validate presence of at least one eligible Xenite; on resolve, destroy one Xenite and create either OXI or AST.

If no Xenite exists, the only legal action is Hold.

7.2 Defense Swarm / Antlion Array

These ships remain deferred for now. There is an open question whether their “if your health was lower at the start of the turn” condition can be satisfied by existing resolution ordering alone, or whether an explicit start-of-turn health snapshot is required.

Normative status:

Deferred pending dedicated review.

A future implementation pass must decide whether ordering is sufficient or whether authoritative start-of-turn state must be stored.

7.3 Queen

Queen is not ruled out as custom by default. It must be compared directly against the new Dreadnought ship-counting patch in the updated codebase.

Normative interpretation:

Shared shape with Dreadnought candidate: count ships made this turn.

Potential custom requirement: exclude the Xenite created by that Queen from the count.

Status in this document: still deferred, but specifically marked for Dreadnought-parity review rather than assumed-new-framework status.

8. Normative Scope for Phase 4A (Easy Mappers)

Phase 4A must stay tightly scoped to ships whose behavior can be implemented by recombining current frameworks with only value changes or minor computed-effect extensions.

Not in scope for Phase 4A:

New phase structure

New broad targeting system

New destroy-immunity system

New replacement-counting rules that affect other ships globally

Trigger-on-destruction framework

Start-of-turn health snapshot requirement unless a dedicated review proves it is already implicitly available

9. Anticipated Implementation Families in Phase 4A

Flat heal family: Oxite

Flat damage family: Asterite

Charge-choice family: Antlion

Ships-that-build family: Bug Breeder

Count-based computed heal family: Mantis

Count-based + once-only computed damage family: Hell Hornet

Line generation + opponent-distinct-type computed family: Oxite Face and Asterite Face

Minimal/no-op or once-only-on-build family: Xenite, depending on current canonical JSON

10. Risks and Review Gates

Canonical JSON and PDF rules must be kept aligned before implementation begins, even if JSON remains the source of truth.

Computed effect ordering must be deterministic and explicit for any ship whose effect depends on counts or once-only state.

Any ship that appears to require shared turn ledgers, start-of-turn snapshots, or global counting overrides must be moved out of the easy-mapper pass immediately.

Queen must be re-reviewed against the updated Dreadnought patch before it receives a dedicated pass classification.
