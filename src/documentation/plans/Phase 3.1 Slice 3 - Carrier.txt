But: those buttons currently aren’t wired to server choice actions in this phase (see sections below).

✅ “This slice validates CreateShip + spend charge + phase ordering”

On the server, the underlying primitives are already real and correct:

EffectKind.CreateShip is implemented in:

/src/supabase/functions/server/engine_shared/effects/applyEffects.ts

It creates a new instance, and if the created ship def has charges, it initializes chargesCurrent correctly.

EffectKind.SpendCharge is implemented in:

/src/supabase/functions/server/engine_shared/effects/applyEffects.ts

It supports amount > 1, so Carrier’s “fighter costs 2 charges” works naturally.

“Once per turn per ship instance” is already enforced via:

/src/supabase/functions/server/engine_shared/resolve/resolvePowerAction.ts

It writes to turnData.chargePowerUsedByInstanceId on the server.

So: CreateShip and SpendCharge are ready. What’s missing is: exposing Carrier as a structured “choice” in build.ships_that_build and projecting it to the client as availableActions.

2) The real gaps you need to close
Gap A — Carrier has no structured power overlay yet

Your structured powers overlay file explicitly lists Carrier as pending:

/src/supabase/functions/server/engine_shared/defs/StructuredPowers.overlays.ts

Interceptor is implemented there; Carrier needs the same treatment.

Gap B — Server “availableActions” doesn’t emit choice actions for build.ships_that_build

Right now:

/src/supabase/functions/server/routes/game_routes.ts

computeAvailableActionsForRequestingPlayer(...) only derives choice actions for:

battle.charge_declaration

battle.charge_response

For build.ships_that_build it falls back to fleetHasAvailablePowers(...) and returns { kind: 'phase_input' }.

That’s not enough. For this slice you need per-instance choice actions, same as Interceptors.

Gap C — Variable charge costs per option (Carrier) require per-option eligibility

Your current “choice actions” projection checks only power-level chargeCost (default 1).
Carrier has 1-charge option and 2-charge option, so the server must:

include only choices that are legal for that instance right now, or

include all and let the client get rejected (bad UX)

You want this extensible, so do it properly now:

server emits choices: [{choiceId}, ...] filtered per-instance based on chargesCurrent and each option’s chargeCost.

Gap D — Client only treats charge phases as “server choice phases”

On the client:

/src/game/client/gameSession/mapVm.ts

It only uses availableActions to build ShipChoice groups during charge phases.

For build.ships_that_build it derives from fleet counts (which will be wrong: includes depleted carriers, can’t disable “fighter”, and can’t map to instance IDs).

And:

/src/game/client/gameSession/intents.ts

runReadyToggleFlow only batch-submits ACTIONs in charge phases.

You need the exact same flow for build.ships_that_build.

Gap E — Board rendering is currently incapable of showing “Carrier graphic state by charges”

This is important given your “7 graphic states” requirement.

Right now BoardStage always calls:

resolveShipGraphic(..., { context:'live', currentCharges: null })
in:

/src/game/display/layout/BoardStage.tsx

So it will never select charges_5/charges_4/etc based on state.
Interceptors “worked” visually because you were using the condition split stacks for maxCharges==1, not because BoardStage was reading chargesCurrent.

For Carrier (maxCharges=6), you need BoardStage to pass actual currentCharges per rendered entry (or otherwise provide explicitCharges).

This also sets you up cleanly for Bug Breeder later: same mechanism, different overlay.
