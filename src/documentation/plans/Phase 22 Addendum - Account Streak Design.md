### 2.1 Data model and access — set 05

**P1 — Three tables, no operations table.** Simplest design: one current row, one per-game application ledger, one consumed-anchor ledger. Reason: these respectively solve account serialization, duplicate results and import replay; no historical statistics tables are needed. Rejected: embedding accounts in KV, an event-sourced streak service, separate run-history tables, or a fourth operations table without a concrete uncovered failure.

All times below are UTC `timestamptz`; fields are NOT NULL unless marked `?`. Independent IDs are UUIDs; game/player IDs remain text. Counts use bigint constrained to `0..9007199254740991`, preserving existing numeric clients; revisions use positive bigint and travel as decimal strings. No FK into KV JSON, no device/IP fields, no credentials in these tables.

| Table | Columns and constraints | Indexes / simplest need |
| --- | --- | --- |
| `public.account_streak_runs` | `account_id uuid` PK/FK accounts ON DELETE CASCADE; `run_id uuid`; `current_count bigint` default 0; `revision bigint` default 1; `tracked_game_id text?`, `human_player_id text?`, `tracked_status text?` checked `unfinished/settled/retired/restart_pending`; `ended_count bigint?` positive, `ending_game_id text?`; `created_at`, `updated_at`. Tracked tuple is all-null or all-present; ended pair is both-null or both-present. Run identity rotates on a reset/new selected run, not every result; revision increases on every visible mutation. | Account PK is sufficient for current state. **P2 — Use one short atomic game/run RPC where both must change.** Reason: same-database transactions remove the creation/enrollment gap without a saga. Rejected alternatives and their actual costs:

| Approach | Failure behavior / complexity | Recommendation |
| --- | --- | --- |
| (a) Atomic RPC | Edge builds canonical candidate and `game_head` with existing TypeScript helpers. RPC locks/rechecks the account run and bounded KV source rows, checks revisions/bonus/account participant, inserts the fresh game and empty history, and updates the ledger/run in one transaction. Any failure rolls back all those writes. A lost response is recovered from the account’s selected game; never blindly replay a create request. | **P2 recommended.** No rules engine in SQL; SQL validates authorization, expected versions and persistence invariants. Preserve `value`/`game_head` agreement and existing history structure. |
| (b) Create first, enroll by CAS | Guest-compatible creation persists a game, then account enrollment checks expected run revision and game ID. Failed enrollment leaves a playable but non-counting game; retry of the same ID is idempotent. It needs explicit recovery and must never show enrollment failure as a counted game. An old failed game cannot later enroll after loss/reset using a fresh revision. | Viable smaller adapter change, but not recommended: partial success introduces avoidable handling for game bonus, existing-run retirement and which game the player should enter. Record it for comparison, not as the default fallback. |
| Operations table / worker saga | Could be needed if a future operation must coordinate an irreversible external effect or unavoidably span transactions and must resume after process death with no recoverable game/run evidence. Neither condition exists here. A response lost after atomic commit is not such a case: the tracked game and ledger survive. | **P2 reject for now.** No concrete uncovered failure justifies the fourth table. If one is found during implementation planning, name it and amend this record before adding machinery. |

**P3 — Lock and compare, then apply exactly once.** Simplest design: existing account → token → session-link authorization order, then run row, then bounded game rows in stable game-ID order, then ledger writes. Reason: serialize results, import and reset against each other and existing revocation. Rejected: worker-local locks, “largest count wins”, or making the 15-second identity cache sufficient for account writes.

- Revalidate token security version, account status and link inside account mutation transactions, including after waits. Use a 2-second lock timeout and bounded rows/retries within the 8-second API budget. Do not hold locks while computing engine state or making HTTP calls.
- Account run creation uses insert-if-absent followed by locking/recheck. Canonical source state changes during preparation produce a revision conflict; the Edge recomputes from fresh state rather than committing a stale result or bonus.
- Reconcile the selected game from persisted canonical state inside the locked transaction before comparing runs or resetting. Check ledger disposition/run identity as well as game ID. A retired or unselected result cannot change a new run.
- An idempotent retry returns the current snapshot, not an old success snapshot/count. Do not add an operations UUID protocol merely to duplicate these game/run identities.

**P4 — Small service-role RPC boundary.** Reason: keep atomic behavior testable behind an injected repository. Rejected: browser queries, arbitrary table patches or a generic client-selected database action.

| Proposed RPC | Inputs from the trusted Edge boundary / atomic behavior |
| --- | --- |
| `account_streak_reconcile` | Account token digest and validated session ID when required; initialize/lock the run, reconcile its one tracked canonical game, return the full snapshot. No client count/result is authoritative. |
| `account_streak_commit_game` | Token digest, validated S, expected run revision, action `create/rematch/restart`, expected source game/revision where applicable, server-prepared candidate/head/empty history. Reconcile/recheck, retire/reset when appropriate, persist and enroll atomically. Restart replay follows the stored reciprocal link and does not reset a newer run. |
| `account_streak_reset` | Token digest, S and expected revision; reconcile then zero/retire under lock. Does not resign/delete the old game. |

### 2.2 Signed-in lifecycle and authority

**P6 — Reuse canonical outcomes and fixed bonus application.** Simplest design: the account ledger changes only the selected run; the existing engine still decides results and applies turn-one bonus. Reason: avoid a second rules lifecycle. Rejected: client result writes, incrementing on screen mount, or recalculating a live game’s difficulty after import/reset.

| Trigger | Account behavior |
| --- | --- |
| Eligible computer creation | Ignore client `winStreakCount` for a verified account seat, including malformed values in that unused field. Reconcile first. Use current account count unless a fresh game retires an unfinished tracked game, in which case use zero. Store the fixed bot recipient/count once. Guest parsing remains unchanged. |
| Human win / computer win / human resignation | Win increments once; loss/resignation resets once, saving existing ended presentation. Bot resignation is a human win if canonically recorded. Use winner relative to the actual human participant. |
| Draw / restart | Preserve count on canonical draw. Restart source never increments or becomes a loss; its selected replacement starts at zero and has the normal fixed zero bonus. |
| Timeout | Apply the persisted canonical winner/draw just like other results. Cover intent, game read/head maintenance and reset maintenance paths. No invented abandonment timer. |
| Abandon tab / logout | No immediate loss. Untimed unfinished game remains selected; timed game resolves under existing clocks. Logout suspends account-seat actions under LA6, without changing the count. |
| Menu Reset | Under lock reconcile any completed result, retire the selection and set zero/new run identity; preserve the old game and its history/bonus. |
| Early in-game restart | Existing eligibility rules; atomic account path stores reciprocal source/replacement links, fresh zero-bonus game/history and zero-count selection. Keep completed replay and existing pending-source recovery semantics. Guest multi-step pending recovery is unchanged. Account-path failure rolls back, rather than requiring a new operations table. |
| Later in-game Reset | Require canonical resignation/finished loss first, then ordinary zero-count rematch. If resignation committed but creation failed, the run stays legitimately zero; retry must not replay resignation or restore the old count. |
| Rematch | Reconcile the finished source and current tracked game before creating; inherit existing timing settings and validate the new assigned name. Rematching an old source while another selected game is unfinished has the same fresh-game reset consequence. |
| Stale tab / second device | Adopt newer server revision even if count is lower. Conflicting mutation returns 409 with current state; refresh before a new deliberate action. No automatic conflict retry that changes selected game or converts a retry into another reset. |

**P7 — Post-commit settlement plus mandatory repair at account seams.** Reason: existing intent/read contracts must survive a temporary streak write failure. Rejected: making account success a prerequisite for returning an already-committed game action, or relying on the browser to report results.

- After a successful account-authorized terminal game mutation, attempt the ledger update with transaction-time authorization. If it fails, retain the canonical terminal game; next successful account reconcile/import/reset/create reads and repairs it before proceeding. Never mutate the account using a detached/revoked link. A result finishing after logout waits for later valid account reconciliation.
- Read/polling routes do not acquire A authority or add account dependencies. A read-induced timeout remains canonical and is settled at the next explicit authorized account reconcile; the client triggers that after observing a terminal game. Read success does not depend on account availability.
- Guest seats keep their complete existing profile, route, timeout and result behavior, including current browser reconciliation failure handling. Signed-in mutation failure holds the action; it does not borrow the guest’s preserve-count-on-failed-reconciliation policy.

### 2.3 Guest-to-account carry-over

**O/Q1 — Legacy trust recommendation:** verify the offered anchor, human/bot shape, recipient, result and direct S when available; accept at most `min(reconciled local current count, stored bound, 10)`. Reason: retains useful carry-over at the observed difficulty-only stakes without claiming full-run proof. Alternatives: (a) full-run verification is unavailable for existing records; (b) stored-anchor bound without a ceiling leaves historic client-supplied difficulty unbounded; (c) bare capped integers discard usable server evidence. Q1 must be locked before SQL/code.

| Canonical anchor result | Stored bound / handling |
| --- | --- |
| Active eligible game | `appliedCount`; unfinished continuation additionally needs real seat proof, not just matching IDs. |
| Human win | `appliedCount + 1`, with safe arithmetic before the ceiling. Reconcile first so the final win is neither omitted nor counted twice. |
| Draw | `appliedCount`; draw preserves the current run. |
| Human loss/resignation, or known later tracked loss | Zero current progress; ended snapshot is not eligible. Do not fall back to an earlier win to avoid the loss. |
| Restart source / malformed result / unavailable game | Follow a verified replacement where available; otherwise preserve the candidate for explicit resolution and do not invent a result. No automatic integer fallback. |

**P8 — One account-entry comparison after authentication, not repeated max().** Reason: keeps authentication successful even if streak transfer must retry, while protecting later streak mutations. Rejected: embedding unverified progress in credential fields, replaying CAPTCHA/password requests, or comparing local/account maxima on every sync.

1. Capture the current guest profile generation, anchor and original S before any session replacement; do not persist/share raw guest session credentials in localStorage. Complete claim/sign-in/forced change through existing routes, preserving S where currently supported.
2. Fetch/reconcile account state and verify/reconcile the offered guest tracked game. The candidate includes `resultPending` to distinguish an observed unfinished/eligible local record from an already-settled count. If the server finds a now-finished win, add one to the pending local candidate before applying the stored bound/ceiling; already-settled wins are not incremented again. Canonical loss overrides either candidate to zero; draw preserves it. The flag is not proof and cannot raise the stored bound. This also handles completed-game reconciliation when the old credential is missing. Authentication does not itself confer authority over that game. No guest candidate means initialize/read the account state without an import request.
3. Under one import transaction, reread the selected account game and guest anchor at their expected revisions, calculate eligible current counts, consume the identified anchor and select the higher. Tie keeps account. A conflict recomputes from server state, not a new client maximum.
4. If the guest wins and its unfinished human seat is directly proven, persist the durable account/game ledger and add `accountId` to that participant’s current state by CAS, preserving ID/name/gameplay/history and fixed bonus. Never bulk-rewrite historical games or past logs. The run retains that game’s continuation.
5. Retire the unselected account selection without resigning/deleting it. An unselected guest game remains a guest game. Neither may later count toward the selected account run. Consume the offered anchor even when the account wins.
6. After confirmed selection/decline, clear the shared guest count/ended snapshot and retire its old association under the current lock, advancing generation. Fence in-flight creation/observation/recovery by the captured account and guest generations; late guest responses must not repopulate the transferred run. Then display the account cache.
7. A failed/unconfirmed import preserves the guest evidence without optimistic consumption. Signed-in streak-changing actions wait for resolution; ordinary multiplayer/account preferences and existing authenticated game access retain their own rules. Explicit decline uses the account run, consumes a valid offered anchor where possible and retires that local candidate. No new screen is assumed.

- Before new import eligibility checks, resolve an existing anchor tombstone: a same-account retry returns current state without replay; another account is refused. For a new candidate, require a guest human participant with **no stored `accountId` and no account-game enrollment**, even when any stored account would match the signing-in account. Reason: an account-owned game or copied account cache must never become a new guest import after a later loss/reset. Directly adopted anchors remain retryable only through their existing tombstone. This is part of P8’s one-time-transfer boundary, not an additional identity mechanism.

**O/Q2 — Missing original credential:** recommend bounded stored-anchor count acceptance without an owner queue, with no seat transfer based only on IDs. Reason: most imports have direct same-tab proof, and a routine owner queue is disproportionate. Alternatives and the unfinished-seat gap are specified in §2.10; no one may implement an implicit relaxation of seat authority or silently drop supported continuation.

**O/Q3 — Recommend anchor consumption plus shared-profile consumption.** Reason: avoids guest request/storage/write changes during play. Rejected default: a new guest-run authority or lineage protocol for a difficulty count. Exact guarantees and residual limitations:

- Unique consumed anchor prevents that anchor from restoring progress after loss/reset, including from another account or after deletion. Local revision/generation/retirement and account-mode fences prevent cooperating stale tabs from restoring the transferred profile. Never evict server consumption tombstones.
- A genuinely new later guest run can offer a different authoritative anchor after logout; no lifetime “already imported” flag blocks all future guest play. Do not infer run independence solely from `createdAt` or reject an otherwise eligible independent run merely because its game predates another device’s import. The no-lineage choice retains the explicit distinct-anchor limitation below.
- **Residual gap:** different anchors may belong to the same unprovable legacy run. A modified/stale client can create a newer game with an old count; Web Locks absence, disabled shared storage, or copied profiles also weaken browser consumption. Stored bounds and the proposed ceiling limit each concession, but do not prove independence or make all such resurrection impossible. Judd must explicitly lock the bounded exception or choose stronger lineage; do not call it full compliance by proof.
- Clamping an imported count does not rewrite the selected game’s fixed difficulty. Account rejoin verifies durable enrollment and ownership; it must not reuse the guest assumption that the applied bonus must equal the current count after a clamp.

**P9 — One scoped effective-participant helper and one game binding per tab session.** Simplest design: on explicit account rejoin, authorise the selected computer human and store a server-written binding `{gameId,humanPlayerId,accountId}` in the validated KV session; use the token row as authority and keep the session-ID mirror consistent. Use the binding only for that specifically authorised computer human; never the bot, spectator, multiplayer or another guest participant. No route may hand-roll the mapping.

- Two devices may control the same selected human through ordinary game CAS/commit rules. One revision wins; conflicting work refreshes. No device lease, account-session takeover or extra simultaneous-controller system is justified for this phase. Result ledger uniqueness prevents double increments.

### 2.10 Open questions for Judd — 5

1. **Q1 — O: How much legacy trust, and what ceiling?** Options: (a) full-run proof only, which existing local runs cannot generally supply; (b) verify stored anchor/session where available, bound by canonical result and stored bonus, and cap at **10**; (c) bare capped local acceptance. **Recommend (b)** for Phase 22’s difficulty-only count, explicitly as a bounded migration concession. Neither historic server-stored difficulty nor the CSV proves all previous wins. Ranked/Stats use requires a new review.
2. **Q2 — O: What happens without the original valid credential?** Most legitimate transfers use the same tab’s claim/sign-in S, so directly prove the tracked human. For the remaining cases compare:

   | Option | Procedure / workload / limitation |
   | --- | --- |
   | **(a) Bounded stored-anchor acceptance — recommended, no owner queue** | Match the local tracked or last-completed anchor’s game/human IDs to stored human/bot data, bound the current count by canonical result/bonus and Q1’s ceiling, and consume the anchor. Does not prove identity or permit seat takeover. A completed game needs no continuation. For an unfinished game, IDs alone cannot satisfy the locked continuation contract: **owner must choose whether to require recovered proof/decline that candidate or explicitly approve a count-only migration exception**. No silent seat grant or silent promise of continuation. |
   | (b) Pending owner review | Keep the candidate locally and show pending feedback; no optimistic transfer. Player supplies account name and game/human IDs through existing support. Owner uses a postgres-only bounded lookup of account revision, anchor/result, consumption and provenance; seeks existing session/account proof, not a display-name match. If proof returns, use normal transfer; otherwise any capped count exception requires an explicit owner note and a postgres-only atomic operation checking expected revision and consuming the anchor. No unproven seat transfer. Missing game/proof that cannot support even an exception is declined. Each case requires a support exchange, lookup, decision, possible manual mutation and follow-up; a lost local pending record has no automatic queue recovery. This option needs its lookup/exception routine and UI specified before implementation and is not the default. |
   | (c) No import without direct proof | Explain the refusal, preserve the local evidence until explicit decline/retry and use the account run. Lowest owner workload, but sacrifices carry-over for these legitimate users. No automatic deletion or claim that their run never existed. |

   **Recommendation:** (a) for bounded count acceptance, with the unfinished-seat subdecision explicitly locked before 22D.1. This unresolved authority boundary is part of Q2, not a sixth question. Do not implement an owner queue by default.
3. **Q3 — O: Is anchor/profile consumption sufficient, or add guest lineage?** **Recommend anchor consumption plus shared-profile consumption/reset** at the observed stakes. It prevents the same anchor replay and normal sibling-tab continuation without new guest-play requests/storage fields/server writes. Explicitly accept or reject the bounded distinct-anchor/stale-client residual risk. Alternative: server-minted root/receipt lineage with every guest impact listed in §2.3; it strengthens new-run verification but cannot retroactively prove legacy runs and must not block guest play.
4. **Q4 — O: How should an isolated signed-in streak outage appear?** **Recommend the existing loading/inline error/retry surfaces**, cached display only after a successful account snapshot, and holding streak-dependent mutations until retry. Existing game/account authority and Entry fallback remain unchanged. Alternative: return to Entry for every streak outage. Lock the precise feedback/decline placement in the later client brief; no new screen assumed.
5. **Q5 — O: Should general account-seat continuation follow later?** **Recommend selected computer streak game only in 22D, defer broader continuation.** Alternatives: keep general account/multiplayer seat continuation out indefinitely, or commission a separately scoped future design/pass for it. Any expansion needs an explicit owner brief covering all seats and concurrency; the helper’s existence is not that approval.
