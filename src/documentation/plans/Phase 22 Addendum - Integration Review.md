## 3. Finding details

### IR1 — Guest Entry can disagree with its cached session name

- **Severity:** should. A guest presentation/identity mismatch; no claimed-name ownership bypass is established.
- **Evidence:** `src/App.tsx:229` routes browser Back to guest Login without clearing S. `src/App.tsx:347` calls `ensureSession(displayName)` and then publishes the submitted player name. `src/utils/sessionManager.ts:160` returns a cached token/session ID without rebinding its existing display name. `src/supabase/functions/server/accounts/gameRequestIdentity.ts:234` prefers the server-bound session name over the guest hint. Explicit Change Name takes a different path through `src/App.tsx:417`, which clears the session.
- **Reproduction to verify:** enter as one permitted, unclaimed name; create/open a game; use browser Back to reach Entry, or reload the root URL in that tab without choosing Change Name. Enter a different permitted, unclaimed name and create/join a game. The menu can show the second name while canonical game identity uses the first.
- **Expected / source:** main plan §4.1 and §5.1 require normal guest entry and preserved navigation; account-design L7 / §2.6 require server-approved name assignment. The submitted guest identity and canonical new-seat identity must agree. This does not authorise renaming existing participants or replacing S during account sign-in/claim.
- **Proposed fix:** at explicit guest Entry submission, distinguish unchanged-name reuse from a deliberate different guest name. Use a fresh named session for the latter before publishing success, keeping account claim/sign-in/forced-change session preservation intact. Do not globally change `ensureSession` to replace identity during games.
- **Follow-up:** 22E.2, Client/UI, small. Add a focused callback/transport regression for browser-Back/root-return with an existing named session, alongside unchanged-name reuse and account sign-in preservation.

### IR2 — Join failure and expired-session recovery are not visible enough

- **Severity:** should. Applies to guest and account paths; it can prevent access to both play and spectating after a failed initial join.
- **Evidence:** `src/game/client/gameSession/clienteffects/useNetworkingEffects.ts:145` records a join attempt; terminal failures at lines 255, 260 and 282 only log and return. The effect has no explicit retry action; polling stays gated at line 369 while `hasJoinedCurrentGame` is false. `src/game/display/GameScreen.tsx:191` consumes only `vm` and `actions`, although `src/game/client/useGameSession.ts:8654` also returns `loading` and `error`. The bootstrap branch at `GameScreen.tsx:281` renders LOADING GAME without recovery controls. For expired S, `src/supabase/functions/server/index.tsx:201` returns the existing legacy 401 body; `src/utils/sessionManager.ts:408` revalidates account-authority codes but does not classify that game-session expiry here. Polling treats 401 as a generic failure (`useNetworkingEffects.ts:467`).
- **Reproduction to verify:** open a nonexistent invite; fail the initial join request once; or use an expired game session when opening/reloading a game. Also expire S after a full state has loaded. Initial failures can leave the loading surface indefinitely; later expiry can leave a stale board with failing requests. A normal network recovery does not itself re-run a completed failed join effect.
- **Expected / source:** main plan §10 22E / §14 require retained invite, rejoin, spectator and return paths; account-design L7 explicitly forbids automatic session replacement during a match. Failures need an actionable route out while preserving identity and canonical state.
- **Proposed fix:** expose bounded join/poll failure state through the existing runtime and game/loading presentation. Offer an explicit retry where appropriate and a return action; distinguish missing game, transient failure and expired S. Preserve the requested game context, never replay gameplay mutations or silently mint a new participant during the match. Any explicit new Entry session follows the existing 24-hour/session-continuation limits.
- **Follow-up:** 22E.3, Client/UI, medium with IR3. Verify failed join then deliberate retry, missing invite then return, expired S before/after initial state, and cancellation after logout/account replacement. No new navigation screen is proposed.

### IR3 — Multiplayer rematch failures have no player feedback

- **Severity:** should.
- **Evidence:** `src/game/client/useGameSession.ts:6944` sends multiplayer New Game through `/new-game-from/:id`; failures, invalid success payloads and exceptions at lines 6960–6976 only log. Computer rematches instead use `winStreakGame.actions.requestBotRematch`, and line 6909 wires its error to the existing New Game helper text. The server preserves multiplayer rematch creation/chat invitations at `src/supabase/functions/server/routes/game_routes.ts:1758` and line 1887.
- **Reproduction to verify:** finish a multiplayer game as a guest and as an account player; make the New Game request fail. The player stays on the old game without an inline explanation. No automatic create replay is present, which should be preserved.
- **Expected / source:** main plan §10 22E path review and §14 retain rematch behaviour and usable account failure handling; account-design LA7 uses existing inline operational feedback.
- **Proposed fix:** route multiplayer rematch pending/error state to the existing end-of-game helper surface, fence completion by game/session identity, and allow deliberate retry without automatic request replay. Keep the server-issued destination/chat invite and current timer inheritance.
- **Follow-up:** 22E.3, Client/UI. Check guest/account failure feedback, late success after leaving the source game, and a successful invite received by the opponent.

### IR4 — Prohibited credential diagnostics remain in the networking seam

- **Severity:** should. Token-prefix output is DEV-gated; the raw-header branch is defensive and is not shown to be reached by correctly constructed production requests.
- **Evidence:** `src/utils/sessionManager.ts:119` logs the received Authorization header at line 129 on misuse; its DEV request log at line 390 derives and prints a game-token prefix. Account-design L15 (`Phase 22 Addendum - Account Design.md:306`) expressly prohibits account/game tokens including prefixes and names these two legacy diagnostics for removal/redaction when this seam is touched. The seam has since been integrated with account transport.
- **Expected / source:** L6 / L15 permit safe outcome/category logging, never credentials, prefixes, raw credential headers or CAPTCHA proofs.
- **Proposed fix:** remove token/prefix/header contents from both diagnostics. Retain safe session/request categories and error codes if useful. Keep the existing anon-gateway versus game-session header separation and account privacy middleware.
- **Follow-up:** 22E.4, Client/UI, small. Use synthetic markers to confirm diagnostic output contains no credential/header values; do not test with real secrets or print them in the review.
